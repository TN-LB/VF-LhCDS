## 一 项目究竟要解决什么问题

输入是一张无向简单图，以及两个参数：`h` 指关注多少个点组成的完全连接结构，`k` 指最多需要多少个结果。`h=2` 时关注边，`h=3` 时关注三角形，`h=4` 时关注四个点两两相连的结构。这种结构称为 h-clique，下文简称“团”。

一个点集的团密度，等于它内部的 h-clique 数量除以点数。例如，一个三角形在 `h=3` 时包含一个团、三个点，密度是 `1/3`。这个密度不是通常的“已有边数除以所有可能边数”。

目标 LhCDS 还要满足连通性、紧致性和极大性。直观地说，集合中的点需要共同支撑相应的团密度，而且不能继续扩展成满足同一紧致性阈值的更大集合。紧致性的具体检查是：删除任意非空的一组点，损失的团数不得小于“密度阈值 × 删除点数”。极大性不能只靠尝试添加单个点来判断，有时必须同时加入多个点才构成合法扩展。

程序按精确密度从高到低返回前 `min(k,q)` 个结果，`q` 是全部合法结果的数量。同密度时，VF 使用原始顶点编号的字典序确定先后。`k=0` 无效；孤立点和合法的零密度结果会保留。若全图没有任何 h-clique，结果就是原图的普通连通分量，密度均为零。

算法的思路可以理解为：每个团贡献一份收益，每个顶点承担同样的使用代价，查询收益减去代价后的最优点集。改变这个代价，会得到一系列嵌套的最优集合，称为主链。实现通过精确查询和分治定位这些层次，再按证明给出的结构规则提取输出。

**Verification-free 指求解器不再逐个验证候选集合是否紧致、是否极大。** 它利用参数化最优集合的层次结构和结构性提取规则生成结果。这个名称不表示程序不需要测试、不需要输入检查，也不表示免除了最大流计算。开发阶段仍需要独立的外部验证，而这些验证不参与正式求解器的决策。

依据：[算法规范](ALGORITHM_SPEC.md)、[输入输出契约](INTERFACE_CONTRACT.md)。

### M0 统一契约与搭建骨架

M0 把“什么输入合法、如何保留顶点、同分如何排序、失败如何返回、什么算一次查询”等问题固定下来，避免后续模块各自采用不同解释。C++17/CMake 和独立 Python/pytest 工程、严格编译警告、CTest、ASan/UBSan 选项也在这一阶段建立。

四份原始论文文件没有被改写。由于当时不存在更早的 SHA-256 快照，M0 建立的是首次内容快照，之后的检查用于确认文件未变化，不能把它理解成对更早历史版本或研究优先权的证明。现有理论契约没有发现需要重新打开的冲突。[M0 记录](../evidence/m0/REPORT.md)

### M1 独立参考实现

Python 参考程序直接枚举小图中的集合，检查删除条件和所有真超集。它还通过枚举全部集合求参数化最优解，用独立的直线包络方法构造主链，没有调用生产求解器，也没有照搬生产分治过程。

这相当于为后续代码建立一个独立答案来源。其代价是计算量呈指数增长，只适合小图；默认规模保护为 12 个顶点，少数明确记录的诊断使用了 13 点例子。M1 完成了 74 项单元测试，并检查了全部 1–5 点标号简单图在 `h=2,3` 下的 2,198 个图/参数实例，以及另外 100 个固定种子的实例。[M1 记录](../evidence/m1/REPORT.md)

### M2 精确查询部件

M2 实现图、顶点集合、团的物化存储、精确分数以及一个通用 Dinic 最大流算法。“物化”表示先把所有 h-clique 保存下来，后续查询重复使用。

查询时，一个团已经落在已选集合里的部分可以扣除，剩余顶点构成它的 footprint；相同 footprint 合并计数，再构造闭包网络。精确最大流给出参数化目标的最优集合。接口明确区分“某个受限范围内最优”与“全图最优”，只有满足相应包含条件才能承诺后者。

数值计算在安全时使用检查过溢出的 128 位容量，超出安全范围时会自动执行任意精度整数版本，测试实际触发了这条路径。查询内部的同分规则是选最大基数集合；它与最终输出按原始编号排序是两件不同的事。[M2 记录](../evidence/m2/REPORT.md)

### M3 完整求解器与正确性冻结

M3 将查询接入先左后右的分治过程，按密度层次提取结果，并在取得所需 k 个结果后停止。终止判断使用原始区间端点；结果提取使用原图的普通连通分量，还要检查该分量与已有集合之间是否存在边。

这一阶段补齐了完整输出、固定 k 前缀、孤立点、原始编号、大整数、错误状态、外部计时和查询计数。完整链遍历的逻辑查询数检查了 `2r−1` 关系，其中 r 是不计初始空集的主链层数。但逻辑查询并不都需要一次最小割，也不能据此宣称 top-k 只需 `O(k)` 次查询。

Debug、Release、带调试信息的 Release 及 ASan/UBSan 配置均通过当时的 9 项 CTest。完整输出和每个 k 前缀与独立参考比较；测试覆盖穷举小图、1,000 个固定种子实例及更高 h。经代码检查修复了一个被移动后的证书对象问题，随后冻结了可追溯的正确性版本。[M3 记录](../evidence/m3/REPORT.md)

### M4 安全优化

第一项是安全 h-clique-core 缩减：对于满足条件的正阈值查询，移除不可能参与该查询答案的点，缩小最大流需要处理的范围。它只改变查询搜索上界，不改变原始分治端点、阈值或结果提取规则。

第二项是 membership footprint 扫描：用顶点成员标记判断归属，减少反复扫描有序集合的开销。core 开关与两种 footprint 扫描方式组合成四种模式，所有模式都与独立答案和原有输出逐一比较，Debug 与 ASan/UBSan 测试均通过。

正确性等价不代表一定更快。core 自身也需要计算，M4 的局部测量和后来的最终消融都显示，节省的网络工作有时不足以抵消这项开销，因此它始终保留为可选项。[M4 记录](../evidence/m4/REPORT.md)

### M5 实验接入与最终评估

M5 的工作包含四部分：让作者 IPPV 程序能构建并正确处理已发现的问题；建立统一输入和外部比较规则；修复实测暴露的 VF 实现瓶颈；最后冻结版本，执行一轮统一实验并复现结果。

VF 增加了相邻点交集方式的团枚举，以及 membership 团计数。前者减少不可能形成团的组合尝试；后者避免在每次集合计数时反复做长集合扫描。两者仍保存同一批团、计算同样的精确数量，没有改变算法问题定义。

一次针对计数瓶颈的受控比较中，CA-CondMat 的 `h=3,k=5` 耗时中位数从 38.792 秒降到 1.709 秒，两种计数方式的结果和计数器严格一致。这是三个重复、单个设置下的局部优化证据，不能拿来作为最终 VF 对 IPPV 的加速倍数。之后停止优化，采用固定版本完成五次重复的最终评估。[枚举契约](ENUMERATION_IMPLEMENTATION.md)、[计数优化证据](../evidence/m5/counting-20261007/REPORT.md)

## 四 IPPV 的修复与比较边界

最终对比对象是固定作者提交加八个逐项记录在仓库中的补丁，并非未经修改的原始 IPPV。补丁覆盖构建兼容、未初始化计数、存储失效、h=2 枚举、末尾单边分量、验证容量精度、PAVA 工作区和同密度验证边界。补丁内容及哈希均保留在[基线锁定记录](../baselines/ippv/source-lock.json)。

两个直接影响答案的例子值得保留：

- **漏掉合法结果。** 一次 CA-GrQc 比较中，VF 找到密度为 `56/13` 的集合，而 IPPV 漏掉了它。独立的原图证书和小图回归确认了该结果的合法性。原因之一是验证器把本应为分数的容量转成整数，例如约 12.9 被截成 12，改变了原问题；补丁使用共同整数缩放构造精确容量。另一个独立的工作区越界问题也被修复。[诊断与修复](../evidence/m5/ippv/disagreement-20261005/REPORT.md)
- **多报非极大结果。** 最终实验的早期版本在 CA-CondMat 上输出了一个密度 21 的 K10，但它与另一个同密度 K10 通过普通边相连，两者合并仍满足对应紧致性条件。单独 K10 因此不是极大结果。IPPV 的边界比较遗漏了同密度扩展，修复后重跑了受影响的整个主实验。[精确反例与修复](../evidence/m5/ippv/equality-20261008/REPORT.md)

这些修复有具体证据支持，但不代表 IPPV 的整个实现已被完全证明正确。它仍有零密度结果遗漏，其他浮点界与部分旧验证路径也未全面审计；修复后的容量构造仍受其既有整数流后端范围限制。上游许可证尚未明确，当前交付也不包含对外分发其源代码或可执行文件。

DCLDS 保持暂缓，没有继续阅读、比较或接入，也没有把其方法移植进 VF。本项目当前不能据此做覆盖全部主要竞争方法的结论。

## 五 最终实验如何进行

实验使用两份固定并规范化的图文件。它们来自已取得的 IPPV 数据副本，名称相同不代表与网上任何其他版本逐字节相同；比较以保存的文件哈希为准。

| 图 | 顶点数 | 无向边数 |
|---|---:|---:|
| CA-GrQc | 5,242 | 14,484 |
| CA-CondMat | 23,133 | 93,439 |

主实验取 `h=3,4,5`、`k=5,10,15,20`，共 24 个设置；每种算法、每个设置运行 5 次。另有 core 开关消融，以及 `k=5` 与完整输出的提前停止消融。

| 实验 | 算法进程运行数 | 结果比较 |
|---|---:|---|
| VF 与 IPPV 主比较 | 240 | 120/120 对满足截止密度并列规则 |
| core 关闭与开启 | 60 | 30/30 对完整结果严格一致 |
| 前 5 个与完整输出 | 60 | 30/30 对前缀严格一致 |
| 最终合计 | 360 | 全部完成，无超时、OOM 或错误 |

主比较的 120 对中，40 对完全一致，80 对仅在允许的截止密度并列选择上不同。例如第 k 名所在密度层还有多个并列集合，IPPV 和 VF 可能选择不同的并列成员。VF 仍遵守自身固定的原始编号排序规则；比较器没有修改或合成任何一方的输出。不同密度层的遗漏或多报仍会判为失败。通过这项比较表示满足并列兼容规则，不提供大图极大性的独立证明。

测量环境为 Apple M1、16 GiB 内存、macOS 15.7.7、AppleClang 17 的 Release 构建。算法单工作线程、各调用串行执行，每个算法进程和独立验证进程分别限制为 60 秒。IPPV 固定 iterations=10、p=0。没有设置内存上限，没有控制文件缓存，没有预热、失败重试或根据结果增加重复次数；配对执行顺序按固定种子随机化。

耗时是算法进程从启动到退出的整体时间。外部验证在进程结束后进行，不计入算法时间；IPPV 自身算法中的候选验证仍计时。峰值内存用进程 RSS 表示，不是某个单独模块的分配量。

此前的七补丁主实验执行了 182 次后遇到真实错误，58 次未执行；这些记录全部保留，不混入最终数据。加上最终使用的 360 次，两次最终批次尝试实际执行了 542 次算法调用。这个 542 不包含更早的试跑、开发诊断和正确性测试。[完整实验记录](../evidence/m5/final-main-repaired-20261008/REPORT.md)

## 六 最终结果说明了什么

### VF 与 IPPV 各有优势

**VF 在 11/24 个设置的耗时中位数更低，IPPV 在 13/24 个设置更低。** CA-GrQc 上的 12 个设置均为 IPPV 更低；CA-CondMat 上除 `h=4,k=5` 外，其他 11 个设置均为 VF 更低。

其中，CA-CondMat、`h=3` 的四个设置中，IPPV/VF 耗时中位数比约为 1.90–2.09；CA-GrQc 则呈现相反方向。内存结果同样混合，VF 在 10/24 个设置的 RSS 中位数更低。不能将这些结果简化为“VF 全面更快”或“VF 完全不如 IPPV”。

附录给出全部 24 个设置的数字。五次重复的最小值、最大值和原始记录见[完整主实验表](../evidence/m5/final-main-repaired-20261008/aggregate/main/TABLE.md)；以下结论不包含显著性检验。

### core 在这些数据上主要体现为内存取舍

安全 core 在六个图/h 设置中的 RSS 中位数都更低，但五个设置耗时中位数更高。CA-CondMat 的耗时增加约为 17%–50%。这说明“网络可以缩小”不等于“端到端一定更快”，core 计算本身也要付出代价。主实验的 core 关闭设置在运行前已固定，开启结果作为单独消融保留。

### 提前停止有实际作用

`k=5` 在六个设置中的完成时间中位数都低于求出全部结果，而且前缀严格一致。这支持当前实现确实能减少不需要的后续工作。

它不等于“按名次持续流式输出”：当前库先收集所需结果，再由命令行序列化。因此尚未测量的“第一名什么时候出现、每增加一个名次花多久”，不能由这张表代替。

### 图的点数不能单独解释难度

CA-GrQc 的点数更少，但 `h=5` 时出现了 2,215,500 个物化团，最大观测网络有 2,220,744 个正向节点、13,298,242 条正向弧。VF 在该组主实验的 RSS 中位数接近 2 GiB，明显体现出保存团和构造网络的成本。

这个例子说明，只看顶点数可能误判难度，团数和网络规模也需要一起考察。现有证据仍不足以完整解释 VF 与 IPPV 在所有设置上的性能差异；旧版本的细分阶段诊断不能直接当作最终版本的阶段耗时分解。

## 七 正确性与复现证据应如何理解

| 证据层次 | 已经检查的内容 | 不能由此推出的内容 |
|---|---|---|
| 数学说明 | 原始证明、实现规范及优化保持语义的论证 | 不能用测试数量代替一般性证明 |
| 定义级检查 | 小图直接枚举删除集合、真超集和预期输出 | 不能自动覆盖所有大图 |
| 结构检查 | 输出顶点、团数、密度、连通性、排序等 | 单独不能证明极大性与完备性 |
| 跨实现比较 | VF 与修补后的 IPPV 在规定规则下吻合 | 两个程序一致不等于独立真值证明 |
| 特定实例证书 | 对已争议集合给出原图上的精确证明或反例 | 只覆盖相应实例与命题 |

测试包含普通图、桥接结构、同密度并列、断开分量、孤立点、`h>|V|`、大顶点编号、数值边界和真实任意精度回退。参考代码没有调用生产代码。最新计数优化的验收还完成了 14 个参考对照测试批次，1,392,496 条历史响应匹配；这统计的是多模式、多后端等重复执行下的响应记录，不是这么多张不同图。

Debug、Release、ASan/UBSan 的相关验收均有保存的日志。ASan/UBSan 用于发现内存与未定义行为问题；通过表示已执行测试中没有相应诊断，不是对所有未来输入的保证。生产算法没有并行执行，TSan 未作为已完成工作。

另在全新 Ubuntu 24.04.5 arm64 软件环境中，重新安装 Linux 依赖并构建 VF 和八补丁 IPPV。GCC 13.3 构建通过，16/16 CTest、164 项 Python 测试、三项 IPPV 和一项 VF 独立定义检查全部通过；四个例子的规范化输出与 macOS 相同，26 个汇总/审查文件逐字节再生一致。

Linux 环境运行于同一台 Mac 的 OrbStack，共享其 Linux 内核环境和物理硬件。它验证了从新软件环境安装、构建和检查的能力，没有在另一台独立机器上重做性能实验，也没有把完整 sanitizer/穷举批次在 Linux 上全部重跑。[优化验收](../evidence/m5/counting-20261007/REPORT.md)、[Linux 复现记录](../evidence/m5/clean-env-20261008/REPORT.md)

## 八 当前限制和需要核对的结论

目前没有已知而未处理的 VF 语义冲突或最终验收失败；四份原始论文文件保持不变。以下限制仍会影响后续研究表述：

| 项目 | 当前边界 |
|---|---|
| 数据覆盖 | 只有两份固定真实图，不能据此概括一般可扩展性 |
| 基线覆盖 | 对比的是八补丁 IPPV；DCLDS 与专用基线未完成比较 |
| 基线完整性 | IPPV 仍有零密度遗漏、未全面审计的浮点路径及许可证不明问题 |
| 性能环境 | 共用日常主机，非专用空闲机器；没有控制缓存与温度/频率 |
| 指标 | 未提供逐名次时延、最终版本完整细分流阶段耗时 |
| 规模与功能 | 仍物化全部团；未实现流式后端、并行或其他最大流算法 |
| 复现级别 | 新 Linux 软件环境通过；独立硬件性能复测与对外发布未完成 |

主实验前后观测的一分钟系统负载为 2.286–14.694，说明不能假定整段测量中机器空闲。系统也已有交换空间占用，但这本身不足以说明某次算法调用发生了活跃换页。我们保留了所有样本，没有据这些观测事后剔除不利结果。五次重复能显示波动，不能消除环境影响。

因此，当前可以写成“实现了按既定规范工作的精确 VF-LhCDS 求解器，完成了有限但可追溯的实现验证，并在已测两图上观察到与 IPPV 各有优势的性能表现”。暂不应写成“测试证明了定理”“真实图结果已穷举验证”“VF 普遍更快或省内存”“达到全面 SOTA”或“top-k 只需要 O(k) 次查询”。

当前最值得核对的是研究重点：如果主张重点在算法结构、精确实现与可行性，现有资料已能支撑一份完整的阶段说明；如果重点转向广泛性能优势，就需要先确定补充数据和基线范围，再新增实验。现阶段没有自动启动新的优化或实验轮次。
